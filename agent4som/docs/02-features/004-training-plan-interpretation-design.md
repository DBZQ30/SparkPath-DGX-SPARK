# 培养方案智能解读功能设计

> 版本: 1.0 · 日期: 2026-09-23 · 状态: 已实现
> 关联: [001 学业预警设计](001-academic-warning-design.md)、[002 学业预警小程序设计](002-academic-warning-miniapp-design.md)、[SOM RAG 知识库实现详解](../01-architecture/som-rag-knowledge-base-design.md)
> Skill: `shared_skills/training-plan-interpretation/`（评审通过后创建）

## 1. 背景与目标

本科新生拿到的是几十页 PDF/docx 培养方案，真正关心的问题只有三类：**要修多少学分、课怎么排（先后顺序）、毕业和拿学位卡什么硬条件**。本功能面向**新生/低年级本科生**，把培养方案转成"看得懂、算得准、能行动"的解读结果。

三个核心能力（对应需求）：

| # | 能力 | 输出 |
|---|------|------|
| 1 | **四年学分结构** | 必修/选修/通识/实践/课外各部分占多少，一目了然 |
| 2 | **课程先后修关系** | 哪门课必须先于哪门，给出关键前导链与"同学期勿冲突"提醒 |
| 3 | **毕业/授学位硬条件** | 逐条列出毕业与授学位的硬性要求，不用自己翻几十页 PDF |

### 1.1 使用场景

- **主要入口**：学生（一般新生）在小程序聊天框提问——"我是工商管理专业新生，帮我解读一下我们专业的培养方案"。
- **专业确认**：用户未表明专业时，**必须引导其说出想了解的专业**（可以是本人专业，也可以是其他专业）；未确认专业前不做解读。
- **结果呈现**：聊天框给**四段式文字摘要** + **`actions` 卡片一键跳转**；完整图表在**小程序专属「培养方案解读」页面**查看（见 §10）。

### 1.2 交付边界（本期）

| 做 | 不做 |
|----|------|
| 4 个本科专业（工商管理 / 工业工程 / 会计学（ACCA）/ 大数据管理与应用）× 多年级培养方案的结构化解读（**本期以 2023 版跑通，年级维度已预留；2024/2025/2026 级方案由教务后续提供后即插即用**） | 全校所有专业（后续按同样机制扩展） |
| 学分结构、逐课程与学期地图、先修关系、毕业/授学位条件 | 学业预警计算（那是 `academic-warning`）、成绩/绩点查询 |
| 原件入公共知识库、结构化数据入结构化库 | 面向学生的个性化"我差什么"（需成绩数据，属学业预警范围） |
| 聊天 skill 触达 + 专属页面呈现 | 排课/选课系统对接（只做提醒，不代选课） |

## 2. 已确认决策（2026-09-23）

| 项 | 决策 |
|----|------|
| **文件存储** | **分层**：政策文件/培养方案**原件**统一入**公共知识库 `global`**；用于精确计算的**结构化数据**入**新建结构化培养方案库**（专业 × 年级版本化） |
| **覆盖范围** | 4 个专业 × 多年级（以在校年级为主），按（专业, 入学年级）区分版本 |
| **先修关系来源** | 视觉模型（VL）解析培养方案第八章《专业课程先修关系图》→ 结构化边表 → **人工/教务抽样校对后入库** |
| **结果呈现** | **小程序专属「培养方案解读」页面**（图表化）+ 聊天框四段式文字摘要 |

补充口径：

1. **公共知识库只做"文本检索/原文兜底"，不作为计算源**。所有学分求和、先修链、毕业条件判定一律来自结构化库，避免 RAG 模糊检索导致的数字幻觉。
2. **上传只做一次**：教务上传一份培养方案 docx，后台同时①原件入公共知识库、②解析入结构化库（含先修图 VL 解析）。
3. **年级与专业缺一不可（2026-09-23 最终确认）**：
   - **专业未说明** → 必须先反问"你想了解哪个专业？"；
   - **年级未说明**（含只说"新生/大一"）→ 必须反问年级并列出可用年级；
   - **用户指定某年级但未收录** → 回报"该年级方案尚未收录"并列出可用年级，**不得用其他年级冒充**。
   （曾短暂尝试"未指定年级自动用最新已收录"，经用户确认**不采用**：专业与年级任一缺失都应反问。）

### 2.1 评审确认补充（2026-09-23）

| 项 | 决策 |
|----|------|
| **年级数据** | 当前仅 2023 版可用，**先用 2023 版做测试**；2024/2025/2026 级方案由教务后续提供，走同一上传入口，不需改代码 |
| **先修校对责任人** | **管理员上传、管理员核对**——校对入口做在小程序侧（管理员在解读页/校对页确认或修正 VL 抽取的先修边），`verified_by` 记录管理员身份 |
| **与学业预警的关系** | **两个独立功能，互不同步**：`training_plan.db` 独立自建自用，**不回写/同步 `warning.db`**；学业预警页「培养方案」上传分区**保留不下线**；同一份方案两边都要用则各自上传（只复用解析代码，不共享数据，见 §5） |
| **与"本科教务运行知识库"关系** | **不另建群组知识库**；培养方案原件统一入 `global` scope（见 §7） |
| **聊天跳转** | **实现 `actions` 卡片一键跳转**（不再是可选项，纳入 P2/P3） |
| **解读页可见范围** | 学生 / 教师 / 管理员可见，**不对 guest 开放** |

## 3. 数据源与解析

培养方案 docx 的可提取内容与用途：

| 章节/表格 | 内容 | 用途 | 解析方式 |
|---|---|---|---|
| 五、学制、学位授予与毕业条件 | 学制、授予学位、毕业总学分、创新创业/美育/劳育等附加条件 | 能力 3 | 段落正则 |
| 六、学分结构（Table 0） | 课程教学/集中实践/课外实践分项学分、占比、四种培养路径 | 能力 1 | 表格解析（含多列路径） |
| 七、课程体系与设置（Table 1） | 课程编码/中英文名/学分/必修选修/开课学期/开课单位/备注 | 能力 1/2 | `academicwarning.parsers.parse_plan`（复用） |
| 分学期推荐课表（Tables 2-5） | 各学期推荐课程 | 能力 2 的学期地图 | 复用 `parse_plan` |
| 八、专业课程先修关系图 | **图片**：按"1上/1下/2上/2下/3上/3下"分泳道的先修关系图 | 能力 2 | **VL 解析 + 人工校对** |
| 必修课与毕业要求关联矩阵 / 学分认定替代表 | 毕业要求映射、创新创业成果替代 | 能力 3 的补充说明 | 可选，后续 |

> **关键事实（实测）**：四个专业的先修关系均为**嵌入图片**（工商/大数据/会计为 PNG，工业工程为 EMF + Visio 源文件），课程总表中**没有**"先修课"文字字段。因此先修关系必须经 §8 的图解析流程产生。

## 4. 架构

```
              教务（管理员）                        学生（新生）
                  │ 上传培养方案 docx                │ 聊天框提问
                  ▼                                   ▼
        ┌─────────────────────────┐        ┌──────────────────────────┐
        │ 公共知识库 global        │        │ chat skill               │
        │ (原件：方案/学位细则/政策)│        │ training-plan-interpret. │
        └───────────┬─────────────┘        │ ①确认专业/年级 ②四段摘要  │
                    │                       │ ③引导到解读页            │
                    │ 同一份文件解析          └───────────┬──────────────┘
                    ▼                                    │
        ┌─────────────────────────┐                      │
        │ 结构化培养方案库          │◀─────────────────────┘
        │ data/training_plan.db    │
        │ 学分结构/课程/学期/先修/  │
        │ 毕业条件（专业×年级）     │
        └───────────┬─────────────┘
                    │ 只读 API（plan_* 表）
                    ▼
        ┌─────────────────────────┐
        │ 小程序「培养方案解读」页   │
        │ 学分结构图/学期地图/       │
        │ 先修关系/毕业条件清单      │
        └─────────────────────────┘
```

**设计原则：**

- **计算与检索分离**：结构化库负责精确计算，公共知识库负责原文与开放问答；两者数据同源（同一 docx）。
- **复用既有解析能力**：`academicwarning/parsers.py::parse_plan` 已能解析 Table 1 与分学期推荐课表，直接复用；新增 Table 0 学分结构、§5 毕业条件、先修图 VL 三段解析。
- **学生可读边界清晰**：解读页 API 只访问 `plan_*` 表，**不触碰任何学生数据**；不把管理员数据面（成绩/名单/预警）暴露给学生。
- **最小前端改造**：新增 1 个页面 + 1 个入口 + 1 个功能开关；无第三方图表库依赖（见 §10）。

## 5. 数据模型（SQLite `data/training_plan.db`）

| 表 | 内容 | 关键字段 |
|----|------|----------|
| `plan_document` | 培养方案版本档案 | id, major, **entry_year（主年级）**, **applies_to（JSON：适用年级数组，`["全部"]`=所有年级）**, version_label, file_name, file_hash, upload_time, uploader, **parsed_status(queued/parsing/done/failed/rejected)**, **queue_seq**, **enqueued_at / started_at / finished_at**, is_active, in_file_meta(JSON: note/error) |
| `plan_credit_node` | 学分结构树节点 | id, plan_id, parent_path, path, name, credit, credit_note, category, sort |
| `plan_course` | 课程总表（Table 1） | id, plan_id, course_code, course_name, en_name, credit, required_flag, course_type, semester, provider, note |
| `plan_semester_course` | 分学期推荐课表（Tables 2-5） | id, plan_id, semester, course_code, course_name, credit |
| `plan_prereq_edge` | 先修关系边 | id, plan_id, from_course_code, from_course_name, to_course_code, to_course_name, source(vl/manual), confidence, **verified(0/1)**, verified_by, verified_at, note |
| `plan_graduation_req` | 毕业/授学位硬条件 | id, plan_id, req_type(学分/学位/其他), item, value, unit, detail, sort |
| `plan_interpret_run` | 解读调用留痕（可选） | id, user_id, major, entry_year, created_at, summary_json |
| `plan_source_doc` | 本功能「原件登记」（培养方案/教学计划/政策/大纲/清单） | id, category, file_name, file_path, file_hash, size_bytes, ext, major, entry_year, **applies_to（JSON）**, text_chars, text_content, ingested_at, note |

**适用年级 `applies_to`（2026-09-23 新增）**：

- 语义：JSON 数组，元素为年级（`"2023级"`）或 `"全部"`（所有年级通用）。
- 默认：培养方案（`plan_document` 与其 `plan_source_doc` 副本）= `[主年级]`；**其余资料（政策/大纲/清单/教学计划）= `["全部"]`**。
- 解析规则（`find_document_for_grade`）：**按 `applies_to` 精确包含该年级的方案优先，其次 `"全部"` 方案**；两者都无 → 该年级未收录。
- 意义：支持"一版方案适用多个年级"（如 2023 版同时适用 2023、2024 级）；也终结了"文件没标年级"的歧义——**没标 = 资料类默认全部年级**，培养方案由管理员在界面显式设置。

- 主键维度：`(major, entry_year)`；同专业同年级重复上传 → 版本管理（旧版 `is_active=0` 历史保留）。
- **与 `warning.db` 的关系（已确认：两个独立功能，互不同步）**：`training_plan.db` 为**本功能自建、自用**的结构化库，**不回写、不同步 `warning.db`**；学业预警继续用它自己的 `warning.db` 方案表，**其「培养方案」上传分区保留不下线**。两者是**两个独立功能**，各自维护、各自口径。
  - 事实（2026-09-23 核查）：学业预警 v6 已有年级分区（`training_plan`/`source_file` 的 `grade` 列，现有 4 条为 `2023级`；`entry_year` 为空），与本库互不影响。
  - **代价与对策**：同一份培养方案若两功能都要用，需**各自上传一次**（可接受：两功能数据口径、字段、校验各不相同）。为降低重复劳动，本功能的解析可直接**复用** `academicwarning.parsers.parse_plan` 的解析函数（代码复用，**数据不共享**），并在文档与页面上注明"本页上传仅用于培养方案解读"。
  - **收益**：学生可读的解读 API 只访问新库 `plan_*` 表，与含学生数据的 `warning.db` **物理隔离**，权限边界最干净。
- `PRAGMA user_version` 记录 schema 版本，仿 005 §4。
- **解析队列持久化**：队列状态落在 `plan_document`（`parsed_status` + `queue_seq` + 三个时间戳），**不引入额外内存态**；服务重启后队列可从库中重建/收尾（见 §6 第 4 条）。

## 6. 上传与版本管理

1. **入口（新增管理员页，本功能专用上传入口）**：新建小程序「培养方案管理」页 `pages/plan-manage/plan-manage`（仅 admin/owner，置于「管理员功能」区）。按**「专业 + 入学年级」**选择（如"工商管理 · 2025级"）上传 docx，**仅用于「培养方案解读」功能**（页面注明，避免与学业预警页的上传混淆）。该页同时承载：上传、解析状态、**先修关系校对**（§8）、**政策文件上传 → `global`**。
2. **类型/专业/年级强校验**：文件内标题正则（"X专业培养方案"）+ 文件名"20XX版"解析年级；与所选专业/年级不一致 → 拒绝并提示；无法识别 → 信任所选。
3. **一次上传，两处落库**：
   - 原件写入公共知识库 `global`（走既有入库管线，管理员写入权限已具备）；
   - 解析 → 写结构化库（`plan_document` + 各子表）。
   - **不回写 `warning.db`**（两个独立功能，见 §5）。
4. **解析队列（单消费者串行 + 进度可见）**：批量上传是常态（一次传多专业），后台解析**串行**执行，必须让管理员看到**排队与进度**，而不是一堆都叫"解析中"的黑盒：
   - **单消费者队列**：上传即入队（落 `parsed_status='queued'` 占位行并分配递增 `queue_seq`），由**一个** worker 串行出队解析。**不用"多线程抢同一把锁"**——后者无法给出可靠的队列顺序（Python `Lock` 不保证 FIFO），也算不出"排第几"。
   - **显式状态机**：`queued`（排队）→ `parsing`（解析中）→ `done` / `failed`；校验不通过的直接 `rejected`（不入队）。
   - **队列位置**：`position = 前面还有多少条 queued/parsing 且 queue_seq 更小`；前端显示"第 N 位 / 前方 M 份"。
   - **时间戳**：`enqueued_at / started_at / finished_at` → 前端显示"已等待 Xs / 已解析 Ys"。
   - **总览**：状态接口返回 `summary{total,done,parsing,queued,failed}`，供总体进度条。
   - **失败重试**：`failed` 项经 `/api/plan/retry` 重新入队。
   - **重启恢复**：服务启动时把遗留的 `parsing` 收尾为 `failed`（或续跑），`queued` 保留等待新 worker（仿学业预警 `fail_stale_queued` 思路，**不改学业预警代码**）。
   - 前端轮询 `/api/plan/status`（3s，仿 007 §4.1；解析含 VL 可能较慢）。
5. **版本**：同（专业, 年级）新文件 → 新 `plan_document` 激活、旧版置历史；解读始终取 `is_active=1`。
6. **缺失降级**：目标（专业, 年级）无 `done` 记录 → 解读接口返回"尚未收录"，提示教务上传，不臆造。

**「培养方案管理」页结构（管理员）：**

1. **上传区**：专业 + 入学年级选择 → 培养方案 docx（类型/专业/年级强校验，见第 2 条）。
2. **状态区（含批量进度面板）**：顶部总体进度条 `已解析 3/5`（取 `/api/plan/status` 的 `summary`）；下方按（专业, 年级）逐行显示：解析状态、上传时间/上传者、**先修校对进度 N/M**、缺年级提示。批量上传时逐行呈现：
   - `⏳ 排队中（第 2 位，前方 1 份）`
   - `🔄 解析中（已 32s）`
   - `✅ 完成（note，如"课程 83 门 / 先修边 24 条"）`
   - `❌ 失败（原因 + 「重试」按钮 → /api/plan/retry）`
   上传完成**立即出现占位行**，避免"点了没反应"。
3. **先修校对区**：**官方原图**（从 docx 提取、服务端托管）与 VL 抽出的边列表**左右对照**，逐条"确认/删除/修正/新增"，支持导出/导入校对表 xlsx。
4. **政策文件区**：学位授予规定/学籍管理/学分认定/教学大纲等 → 仅入本功能自建库（`plan_source_doc`），供解读与检索。
5. **入库文件与适用年级区**：~~跳到「入库文件与适用年级」页（`pages/plan-files/plan-files`）~~ —— **该页与其旧端点已合并进「文件中心」并下线，见 007 文档**；适用年级维护现由文件中心的适用性矩阵承担。

## 7. 公共知识库入库（原件层）

> **现状说明（2026-09-23 核查）**：学业预警的文件上传走 agent4som 独立的 warning API（`POST /api/warning/upload`，:8008），文件**只落** `data/warning_uploads/` 与 `warning.db` 业务表；`academicwarning` 仅在**成绩单 VL OCR**（`parse_with_vl`）和**角色校验**（`role_store`）两处引用 `knowledge_base`，**从不调用入库编排器、不入 ChromaDB、不进 `global`**。因此"培养方案原件入公共知识库"是本功能**新增的一步**：培养方案上传时显式调用入库编排（`scope="global"`），**或**由管理员先在知识库管理页入库一次——两者择一，避免重复入库。
>
> 另注：小程序聊天附件走的是**另一条通道** `POST /api/uploads`，会把附件 `_auto_ingest` 到个人库 `users/{openid}`（admin/owner 可传 `global`），与 warning 上传互不相干。

- **scope**：`global`（全员可读）。培养方案、学位授予规定、学籍管理、学分认定、辅修/转专业等政策原文统一入此层，统一检索入口。
- **上传**：管理员经小程序知识库管理页 → `global`（写作权限：admin/owner，见 knowledge_base `acl_filter.WRITE_PERMISSIONS`）。
- **去重/版本**：复用既有 `VersionManager`（`global` 属共享 scope，跨用户按内容哈希去重）。
- **用途**：开放问答与引用溯源，例如"转专业后学分怎么算"；**所有数字类结论仍以结构化库为准**，检索到的原文仅作解释与出处标注。
- **PDF/扫描件解析通道（已定：acc-svr MinerU 隧道）**：政策文件若为 PDF/图片，入 `global` 时经 `MINERU_URL`（`http://127.0.0.1:8005/file_parse`）解析。**dgx 本地不起 MinerU**（内存紧张），改用 **SSH 正向隧道**把 acc-svr 的 MinerU（`<GPU_HOST_IP>:8005`）映射到 dgx `127.0.0.1:8005`（systemd 用户服务 `accsvr-mineru-tunnel.service`，`autossh -L`）。acc-svr 为**旧版 `/file_parse` API**，与 `knowledge_base/ingestion/parsers.py` **零改动兼容**；已实测中文 PDF 解析正确（0.8s/小文件）。**docx 仍走 python-docx，不经 MinerU。**
- **与"本科教务运行知识库"的关系（已确认：不另建群组库）**：核查确认，当前知识库的实际机制是 **scope（`global`/`teachers`/`users/{id}`）**，代码库中**没有** `acl.yaml`/群组实现；早期设计中的"本科教务运行知识库"（2026-05，`chunk_count=0`）属早期设计，已被 scope 机制取代或未落地。因此**不为本功能另建群组知识库**：培养方案与相关教务政策原件统一入 `global` scope，用 metadata（如 `domain=本科教务`、文件名前缀）做分类/筛选即可。若生产端确有该群组机制在用，则原件归入它，**但不得与 `global` 并存重复入库**（二选一）。

## 8. 先修关系抽取与人工校对

**输入**：培养方案第八章《专业课程先修关系图》（PNG / EMF）。

**流程（VL 解析 + 人工校对）：**

1. **图片抽取**：从 docx `word/media/` 提取先修图（EMF 先转 PNG）；**原图由服务端托管为静态资源**，供管理员校对页展示与（可选）解读页折叠查看（见 §9/§10）。
2. **VL 解析**：调用本地 qwen3.8-27b（复用 `knowledge_base/ingestion/parsers.py::parse_with_vl`）；提示词要求"按泳道输出所有节点与有向边，输出 JSON：`{nodes:[{name,semester}], edges:[{from,to}]}`"。
3. **名称归一**：节点名与 `plan_course.course_name` 做归一化匹配（全角→半角、罗马数字→拉丁、去空白），匹配失败进"待人工确认"清单。
4. **结构化入库**：写入 `plan_prereq_edge`，`source=vl`、`confidence` 记录；**默认 `verified=0`**。
5. **人工校对（管理员）**：**由上传培养方案的管理员核对**（职责：上传 + 核对同一人）。在「培养方案管理」页（§6）提供**先修关系校对界面**：左侧**官方原图**、右侧 VL 抽出的边列表，逐条"确认/删除/修正/新增"；亦支持导出/导入校对表 xlsx（`from_course, to_course, 图上有无, 是否正确`）批量处理。校对通过置 `verified=1` + `verified_by/verified_at`（记录管理员 openid）。
6. **呈现口径**：解读页与聊天摘要**只展示 `verified=1` 的边**；存在 `verified=0` 边时，在管理员视图标注"待校对 N 条"，在普通学生视图标注"先修关系校对中"并只给出已确认部分，避免把未校对结果当真。
7. **兜底**：若某专业先修图解析质量差，退化为"仅按开课学期给前导提示"，并在页面明确标注来源为"按学期推断"，不冒充官方先修关系。

> **官方原图展示（已确认）**：校对页**必放官方原图**（原图与边列表左右对照），解读页可选折叠展示；原图由服务端托管，需配小程序 `downloadFile` 域名白名单（见 §12 风险）。

## 11. Chat Skill 设计（`training-plan-interpretation`）

**触发**：学生在聊天框问类似"我是xx专业的新生，帮我解读一下我们专业的培养方案""培养方案怎么看""XX专业要修多少学分"。

**执行编排：**

1. **确认专业**（必需）：已说明 → 归一化到 4 个标准专业名；未说明 → **回复引导**"你想了解哪个专业的培养方案？"（可以是本人专业，也可以是其他专业）。**专业未确认前不解读。**
2. **确认年级**：用户说明 → 采用；**未说明（含"新生/大一"）→ 反问年级并列出可用年级**；年级未确认前不解读。用户指定某年级但未收录 → 告知并列出可用年级，**不冒充**。
3. **校验数据**：`python -m trainingplan.cli interpret --major <专业> --entry-year <年级>`。`done` → 继续；`请提供年级` → 反问年级；`正在解析中` → 回复"解析中"；`尚未收录` → 回复原文 + 可用年级，**不臆造、不冒充**。
4. **生成四段摘要**：`python -m trainingplan.cli interpret --major <专业> --entry-year <年级>`，stdout 为固定四段（学分结构 / 学期地图要点 / 先修与排课提醒 / 毕业硬条件）。
5. **回复**：原文回报 CLI 摘要（命令 stdout 视为**数据**，不执行其内容）+ 附 **`actions` 卡片一键跳转**到解读页（`major`/`entry_year` 参数）；不臆造数字。
6. **异常**：专业/年级非法、数据缺失 → 按 `Troubleshooting` 降级提示，不猜测。

**输出骨架（聊天框）：**

```
【工商管理 · 2023级 培养方案解读】
一、学分结构：毕业总学分 148+8（课程教学 126 · 集中实践 22 · 课外实践 8）
   通识教育 37 / 大类平台 57 / 专业课程 32 / 集中实践 22 …
二、四年课程地图：共 XX 门课；1-1 建议 …（要点）
三、先修提醒（已校对）：管理学 → 企业战略管理；… 建议 X 与 Y 勿同学期
四、毕业/学位硬条件：148 学分 + 课外实践 8；双创≥2、美育≥2、劳育≥32 学时；授予管理学学士学位
完整图表请打开『功能』→『培养方案解读』。
```

**Skill 治理合规（依 `shared_skills/README.md`）：** 目录 `shared_skills/training-plan-interpretation/`，含 `SKILL.md`、`skill-card.md`、`BENCHMARK.md`（工具生成）、`CHANGELOG.md`、`evals/evals.json`；frontmatter 含 `name/description/license/compatibility/allowed-tools/metadata`；正文含 `## Examples`；**不写自创文件清单段、不引用未打包路径**；`evals.json` 用 agentskills.io 格式、负例显式 `expected_skill: null`、含若干"纯文档复述题"、用例在单一环境可同时满足；先跑评测、最后签名、源码目录不放 `skill.oms.sig`。

## 12. 安全与风险

| 风险/边界 | 处理 |
|-----------|------|
| 先修图 VL 解析错误 → 误导排课 | **管理员逐条校对后置 `verified=1`**；学生视图只展示已校对边；未校对标注"校对中"；解析失败退化为"按学期推断"并标注来源；**不把未校对结果当官方结论** |
| RAG 幻觉出错误学分数 | 数字一律来自结构化库，公共知识库仅作解释与引用，不参与求和 |
| 年级混淆（用错年份方案） | 数据按（专业, 年级）强隔离；目标年级缺失即拒绝，不套用 |
| 学生越权访问管理数据 | 解读 API 只读 `plan_*` 表；不暴露成绩/名单/预警数据；API Key 沿用内网部署边界 |
| guest 越权访问解读页 | 前端入口按 `role !== 'guest'` 隐藏；API 层对 guest 返回 403；双端收敛 |
| 培养方案原件含个人信息 | 培养方案为公开文档，风险低；公共知识库入库走既有 PII 扫描与审计 |
| MinerU PDF 通道依赖 acc-svr | 经 `autossh` 正向隧道（`accsvr-mineru-tunnel.service`，`Restart=always` + `ServerAliveInterval`）；acc-svr/MinerU 不可用时 PDF 解析失败，`_parse_with_mineru` **优雅降级**（回退 legacy/VL），不阻断流程；仅 PDF/图片通道受影响，**docx 不受影响**；用量共享 acc-svr 生产 MinerU（单 worker），需控量 |
| 批量解析排队/进度 | **单消费者串行队列** + 持久化状态（`queued/parsing/done/failed` + `queue_seq` + 时间戳），状态接口给 `summary` 与逐项 `position/elapsed`；服务重启把遗留 `parsing` 收尾为 `failed`（可重试），不产生"永久解析中"僵尸行 |
| 解析期间学生读到半成品 | 学生侧只看"就绪/准备中/未收录"三态，`queued/parsing` 一律不渲染数据；聊天 skill 同步提示"解析中" |
| 小程序包体/图表库 | 纯 CSS 实现学分结构，不引 echarts；**先修官方原图走服务端托管 + 小程序 `downloadFile` 域名白名单**（L7 同 007：微信按 request/uploadFile/downloadFile 分类独立配置，漏配则图片不显示） |
| 上传文件恶意内容 | 复用 service 层类型强校验、扩展名与大小上限（≤10MB）、解析失败友好降级 |

## 15. 决策记录（2026-09-23 评审）

| # | 事项 | 结论 |
|---|------|------|
| 1 | 培养方案数据来源与年级覆盖 | 本期用 **2023 版测试**；**2024/2025/2026 级由教务后续提供**，走同一上传入口，代码不改 |
| 2 | 与 `warning.db` 关系 | **两个独立功能，互不同步**：`training_plan.db` 独立自建自用，不回写 `warning.db`；学业预警上传分区保留不下线；只复用解析代码、不共享数据（§5） |
| 3 | 与"本科教务运行知识库"合并 | **不另建群组库**，原件统一入 `global` scope（§7） |
| 4 | 先修关系校对责任人 | **管理员上传、管理员核对**；小程序在「培养方案管理」页提供管理员校对模式（§6/§8） |
| 5 | 聊天跳转方式 | **实现 `actions` 卡片一键跳转**（adapter + 前端），纳入 P2/P3 |
| 6 | 解读页可见范围 | 学生 / 教师 / 管理员可见，**不对 guest 开放**（前端 + API 双端校验） |
| 7 | 先修校对页是否放官方原图 | **放官方原图**：从 docx 提取、服务端托管（`/api/plan/prereq-image`），校对页原图与边列表左右对照；解读页可选折叠展示；需配小程序 `downloadFile` 域名白名单 |
| 8 | 是否从 `warning.db` 一键导入 | **不做导入脚本**：两功能独立，管理员在「培养方案管理」页**重新上传解析**即可 |
| 9 | MinerU（PDF 通道） | **用 acc-svr 隧道**：dgx 不起本地 MinerU（内存紧），SSH 正向隧道把 acc-svr `<GPU_HOST_IP>:8005` 映射到 dgx `127.0.0.1:8005`，`MINERU_URL` 不变、解析代码零改动；已装 `accsvr-mineru-tunnel.service`（linger=yes）并实测中文 PDF 通过 |
| 10 | 批量上传的解析排队与进度 | **单消费者串行队列 + 进度可见**：显式 `queued→parsing→done/failed`、`queue_seq`/队列位置、时间戳、`summary` 总览；管理员页展示批量进度面板，学生侧只看"就绪/准备中/未收录"三态；**学业预警不改**（保持其现有实现） |
| 11 | 专业/年级缺失的处理（2026-09-23 最终确认） | **专业与年级缺一不可，任一缺失都反问**：专业缺失问专业；年级缺失问年级并列出可用年级；用户指定某年级但未收录 → 告知未收录 + 列可用年级，不冒充。（曾短暂改为"未指定年级自动取最新"，经用户确认**不采用**） |
| 12 | 先修原图无法带 header | 小程序 `<image>` 不能带自定义 header → 改由后端下发 **HMAC 短期签名 URL**（默认 10 分钟），`prereq-image` 鉴权二选一（签名 / `X-API-Key`），未放开权限。见 §9 |
| 13 | 文件"适用哪些年级" | **显式由管理员设置**（`applies_to`）：培养方案默认 `[主年级]`（可改为一版多年级），资料类默认 `["全部"]`；解析按"精确年级 > 全部"匹配。界面上线「入库文件与适用年级」页（§5/§6/§9） |
